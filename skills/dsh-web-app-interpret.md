# dsh-web-app-interpret — 解读回传结果

你不是在解读一段裸数据，而是在读一份**由插件按模板渲染出的用户汇报**。模板是应用在开发期就写好的：回传时插件把变量值填进 `callback.template.md`，经用户确认（若应用未声明 `confirm: false`）后作为用户消息注入当前会话。你的任务是把这段汇报读准，然后继续用户的决策。

## 1. 回传消息的形态

回传消息以 `[webapp 回传]` 开头，携带：

- **应用名与版本**：`应用：<name>（<分支@提交>）`——版本是伺服时盖章的部署指针，不是用户手打的；
- **动作类型**：这次提交代表什么操作（提交配置、确认发布……）；
- **各变量值 + 语义上下文**：值后面跟着模板作者写好的取值含义、单位、空值形态说明。

形如：

```
[webapp 回传] 应用：config-panel（main@a1b2c3d）动作：提交配置
用户在我的「配置面板」里完成了以下设置：
- 目标环境：prod（dev=开发 / staging=预发 / prod=生产）
- 并发数：8（目标并发数，正整数）
...
请基于以上配置继续。
```

## 2. 解读纪律

1. **变量语义以模板作者的声明为准，不要重新发明语义。** `purpose`（`app.json`）和模板里的取值注释就是这个变量的字典。**为什么**：插件只校验类型与存在性，不做语义校验——`TEXT_1` 是环境名还是注释文本，唯一权威来源是作者声明。凭 slot 名字或数值形态猜语义，猜错就是错决策。
2. **以消息里携带的版本为准。** 同名应用的不同版本，变量语义、默认值、甚至动作含义都可能漂移。**为什么**：部署指针随提交移动，你记忆里的「上次那个 config-panel」可能是旧版本；消息头的 `（分支@提交）` 才是这次数据的上下文版本。如果语义和你预期不符，先怀疑版本变了，不要先怀疑用户。
3. **「同一用户在两端各发一次」是允许的。** 去重只拦「同一 turn + 未被压缩/打断 + payload 严格一致」的重复；跨 turn、或 payload 有任何差异（哪怕一个字段值不同），都是一次合法的新提交，照常处理。**为什么**：Q19 定下的规则——用户刻意从全屏和手机端各发一次也照传。不要把它当成 bug 或重复数据去追问「你怎么发两次」。
4. **回传是一次性提交，页面状态不会保留。** 用户提交后，iframe 里的表单状态就丢了（刷新/重开会话也会丢）——这是已接受的设计（Q6）。**为什么**：不要期待「用户上次填的值还在页面上」而设计增量逻辑；如果后续 turn 需要旧值，值在会话消息历史里，不在页面里。
5. **不要因为收到回传就去读应用的 HTML 或仓库。** 你需要的语义上下文模板已经带全了。**为什么**：模板存在的全部理由就是让没有上下文的模型零成本读懂数据；去读源码是设计明确要省掉的 token 开销。只有当你高度怀疑模板与实现不一致时，才在用户的编辑请求下回查。

## 3. 回应方式

- 把回传当作**用户的决策请求**来回应：确认收到、复述关键值（与模板注释核对）、然后执行用户要的下一步。
- 如果值明显不合理（类型对但语义荒谬，如并发数为负数），指出问题并问用户，**不要**静默按错值执行。**为什么**：桥只拦类型与存在性，语义错误只有你能拦。
- 用户要求修改应用本身（改字段、改模板、修 bug）时，切换到 `dsh-web-app-author` 流程（直接改仓库 + git 提交），完成后提醒用户点卡片刷新按钮获取新版本。
