# dsh-web-app-author — 制作/编辑可回传 Web App

你是 dsh-web-app 插件的开发者。你写的不是一个普通网页，而是一个「用户在 iframe 里组数据 → 点击提交 → 插件按模板把数据渲染成用户汇报 → 注入会话驱动模型」的回传装置。全部契约以 `docs/callback-contract.md` 为准；本 skill 是它的操作手册版。拿不准就回查契约文档，不要发明契约里没有的机制。

## 0. 先想清楚要不要做

进入本流程前，先做一次必要性判断：

- **该做**：用户要交互式地组合一组结构化数据（多个字段、有类型、有选项），并且这组数据要作为决策依据回传给模型——例如部署配置面板、发布前检查清单、参数调优表单。
- **不该做**：一句话或一段文字能答的事；用 GenUI 白名单组件就能表达的交互（webapp 走 iframe，比 GenUI 重）；纯展示不需要回传的内容。

**为什么**：webapp 的代价是目录、Git、模板、自检一整条链。数据形状简单或交互简单时，这套链条是纯浪费。

## 1. 目录契约

每个 webapp 是一个文件夹 = 一个 Git 仓库，三件套：

```
apps/<name>/
├── index.html              # 单文件应用（全部内联）
├── app.json                # 元数据
├── callback.template.md    # 回传填空模板
└── .git/                   # 首次部署时由工具初始化
```

规则：

1. `<name>` 必须是 **kebab-case**（全小写、连字符分词，如 `config-panel`）。**为什么**：名字是 URL 路径、注册表键、postMessage 语义的公共标识，大小写/空格会到处漏。
2. 名字**创建后不可改**。**为什么**：注册表、已打开卡片、用户心智里的 `/webapp <name>` 全部绑定这个名字；改名等于换应用。
3. **同名部署一律拒绝**。要给已存在的应用迭代，走 §6 的「直接改仓库」流程，不要重新部署。**为什么**：同名会撞掉既有应用与它的版本历史，用户数据入口被静默替换。

## 2. 单文件 HTML 的内联纪律

`index.html` 必须完全自包含：

- 所有 CSS 内联在 `<style>`；所有 JS 内联在 `<script>`；**禁止任何外部资源**（外链 CSS/JS/字体/图片 CDN）。**为什么**：应用由 host 静态伺服、在 sandbox iframe 里跑，外部依赖意味着不可控的加载失败与安全面。
- 视觉要**深色主题友好**（用 `prefers-color-scheme` 或深色优先的中性配色）。**为什么**：宿主 GUI 有深浅两套主题，浅色写死的应用在一半用户那里没法看。
- 保留占位符词表，**只允许这三个**，出现在 HTML 里（通常在脚本顶部的内联常量）：

  ```
  {{__NAME__}}     # 应用名（伺服时盖章）
  {{__VERSION__}}  # 部署指针「分支@提交」（伺服时盖章）
  {{__TOKEN__}}    # 本次加载的一次性门票 token（伺服时盖章）
  ```

  **为什么**：盖章在伺服响应时发生——仓库存的是带占位符的干净源码，每次加载路由替换出成品。这样 token 每次加载新发、版本号永远是当前部署指针，且仓库零污染。
- **禁止在仓库里自己替换占位符**。写完的源码里 `{{__TOKEN__}}` 必须原样保留。**为什么**：你替换不了正确的 commit hash（鸡生蛋），自己编 token 会立刻被桥的门票校验丢弃。
- 用户直接双击打开磁盘上的源文件时，占位符保持原样、token 失效——这是**可接受的降级**，不是 bug。**为什么**：不经伺服 URL 就没有盖章环节；回传桥在拿不到合法 token 时本就该静默失败。不要在代码里为双击场景做特殊处理，也别向用户承诺双击可用。
- HTML 里**只允许这三个保留占位符**，禁止出现其他 `{{...}}`（如 `{{TEXT_1}}`）。**为什么**：`dsh-web-app-check` 会拒绝任何未声明的占位符；变量占位符只属于模板文件。

## 3. 回传桥（submit 桥）

页面 JS 必须包含提交逻辑，精确执行以下协议：

1. 从盖章后的内联常量读 token；
2. 收集 `values` 对象，**键与类型必须和 `app.json` 的 `variables` 声明严格一致**（`TEXT_n`→字符串、`NUMBER_n`→数值、`BOOLEAN_n`→布尔、`JSON_n`→字符串——即使是 JSON 内容也按字符串传，类型校验只认声明）；
3. 向父窗口 postMessage，消息形**逐字**如下：

```js
window.parent.postMessage(
  { source: "dsh-web-app", type: "submit", token, values },
  "*"
);
```

**为什么**：桥只认 `source: "dsh-web-app"` + `type: "submit"` + 与本次发票一致的 token + 键类型全对的 values，任一不符即丢弃并提示。消息形差一个字段，用户点了提交就石沉大海。

标准可复用的桥模板（页面 JS 以此为骨架，只改「收集 values」部分）：

```html
<script>
  // 伺服时盖章的三个内联常量；仓库源码里保持占位符原样
  const APP_NAME = "{{__NAME__}}";
  const APP_VERSION = "{{__VERSION__}}";
  const APP_TOKEN = "{{__TOKEN__}}";

  function submit(values) {
    // values 的键必须是 app.json 声明的 slot；类型必须与 slot 前缀一致
    window.parent.postMessage(
      { source: "dsh-web-app", type: "submit", token: APP_TOKEN, values },
      "*"
    );
  }
</script>
```

桥之外的要求：

- **不要**写任何初始化/握手代码去「请求 token」或「等待父窗口就绪」。成品 HTML 被 iframe 加载时 token 已经在里面了。**为什么**：Q14a 的盖章方案就是为了让页面零初始化接收代码。
- **不要**监听或发送其他消息类型。**为什么**：协议只有一个方向一条消息，多出来的消息没人接，只会制造噪音。
- 提交按钮点击后给用户本地反馈（如短暂禁用或显示「已提交」），但不要承诺「模型已收到」。**为什么**：消息还要过桥的校验与（默认的）用户确认，页面本身无法知道后续。

## 4. 变量词表与 `app.json`

变量只用固定词表 + 自增编号：`TEXT_1..n`、`NUMBER_1..n`、`BOOLEAN_1..n`、`JSON_1..n`。命名从 `_1` 开始连续编号，不要跳号。

`app.json` 骨架：

```json
{
  "name": "kebab-case",
  "description": "一句话简介，显示在选择器与管理面板",
  "confirm": true,
  "variables": [
    { "slot": "TEXT_1", "label": "展示名", "purpose": "语义声明（你自觉填写）" }
  ]
}
```

规则：

1. **`purpose` 必须写清楚语义**：这个变量代表什么、单位是什么、取值含义是什么（如「目标并发数，正整数」）。**为什么**：`dsh-web-app-check` 只校验类型与存在性，不做语义校验；语义全靠 purpose 与模板上下文承载。解读侧（`dsh-web-app-interpret`）以你的声明为准——你写得含糊，后面解读的模型就会瞎猜。
2. 每个声明的变量必须被模板或页面使用；模板里每个占位符必须有对应的变量声明。两边严格一一对应。**为什么**：这是 check 的硬校验项，多余的声明和孤儿占位符都会被拒。
3. `label` 是用户在界面和确认 UI 里看到的名字，写人话。
4. `JSON_n` 的语义是「JSON 文本的字符串」：页面上用文本域输入，回传值是字符串。**为什么**：桥的类型校验按声明来，页面上把对象直接 post 出去会类型不符被丢弃。

## 5. `confirm` 字段

- 默认 `confirm: true`：回传前向用户展示渲染后的完整文本，确认后才注入会话。**为什么**：这是防伪造回传驱动模型的最终兜底（Q8）。
- 仅当你在开发期判断**回传内容不适合打扰用户**时（例如高频小操作、内容冗长但无风险、用户明确要求免确认），才声明 `confirm: false`。
- 声明 `false` 的代价：**卡片将常驻一条风险提示**。能 true 就 true。**为什么**：跳过确认等于让用户对注入会话的内容失去审查机会，常驻提示就是为此付的 UI 税。
- 无论取值，都要**显式写出**这个字段。**为什么**：check 的 schema 校验要求显式声明，缺省视为你没想过这个问题。

## 6. 回传模板 `callback.template.md`

模板是 Markdown「小作文」，占位符形如 `{{TEXT_1}}`。回传时插件把变量值填进去，作为**用户消息**注入会话。

必须携带四样东西：

1. **应用名与版本**：`{{__NAME__}}` / `{{__VERSION__}}` 保留占位符（这两个在模板里**保持占位符**，回传时由插件填，与 HTML 里的伺服时盖章是两次不同的填充）；
2. **动作类型**：这次提交代表什么操作（「提交配置」「确认发布」）；
3. **各变量值 + 语义上下文**：不止给值，还要给让陌生人读懂值的上下文；
4. 开头用 `[webapp 回传]` 标记，让解读侧一眼识别消息来源。

骨架：

```markdown
[webapp 回传] 应用：{{__NAME__}}（{{__VERSION__}}）动作：提交配置
用户在我的「配置面板」里完成了以下设置：
- 目标环境：{{TEXT_1}}（dev=开发 / staging=预发 / prod=生产）
- 并发数：{{NUMBER_1}}（目标并发数，正整数）
- 附加标签：{{JSON_1}}（JSON 数组字符串，可能为空）
请基于以上配置继续。
```

写作纪律：

- **记住：读这段文字的是一个没有任何上下文的模型**。它没看过你的 HTML、没参与过这段对话的伏笔。模板要把数据写成一段**连贯的用户汇报**——像用户亲口说的话，不是一张裸数据表。**为什么**：模板存在的全部理由就是「让没有上下文的模型读懂这组数据是什么」。
- 每个变量值后面补一句语义注释（取值含义、单位、可能的空值形态）。注释与 `purpose` 保持一致。
- **区分两次填充**：HTML 里的 `{{__NAME__}}/{{__VERSION__}}/{{__TOKEN__}}` 是**伺服时**盖章；模板里的 `{{__NAME__}}/{{__VERSION__}}/{{TEXT_n}}...` 是**回传时**由插件填。两边都保持占位符，都不要自己替换成字面值。
- 模板里只用 `__NAME__`/`__VERSION__` 保留占位符和已声明的 `{{SLOT_n}}`；出现未声明的占位符会被 check 拒绝。

## 7. 部署流程

**首次部署**才调用 `dsh-web-app-deploy` 工具，一次传齐四样：

- `name`：kebab-case 应用名（想好再起，创建后不可改）；
- `html`：`index.html` 完整内容（带占位符的源码）；
- `metadata`：`app.json` 对象；
- `template`：`callback.template.md` 内容。

工具负责：创建 `apps/<name>/`、写入三件套、`git init` + 首次提交、登记注册表（`name → { description, repoPath, deployedRef }`）。**同名会被拒绝**，被拒就换新名，不要在旧名上纠缠。

**首次部署之后的所有修改**，不再调工具，**直接在仓库目录里进行**：用普通文件读写工具编辑 `apps/<name>/` 下的文件，然后 git 提交。**为什么**：仓库即事实源（Q11）；部署指针 `deployedRef = { branch, commit }` 指向主分支最新提交，你提交即部署。

**新版本如何生效**：已打开的卡片实例不会自动更新；用户在对话里点卡片的**刷新按钮**重新拉取部署指针处的成品。你要告诉用户这一点。**为什么**：指针伺服 + 刷新拉新是 Q17 定下的版本机制，模型无法替用户刷新卡片。

## 8. 部署后自检（必须）

每次部署或提交后，**必须调用 `dsh-web-app-check`**（针对该应用目录）。它校验：

1. 三件套齐全：`index.html` / `app.json` / `callback.template.md`；
2. `app.json` 通过 schema 校验（含显式的 `confirm` 声明）；
3. 模板每个占位符都有变量声明；每个声明的变量都被模板或页面使用；
4. `index.html` 含回传桥代码（读取 `{{__TOKEN__}}`、调用 submit）；
5. `index.html` 只使用保留占位符词表，无其他未声明的 `{{...}}`；
6. Git 工作树干净、至少一次提交。

check 不过就修到全过再交付；check 过了但交互复杂（动态校验、条件渲染、复杂输入）时，**用 Playwright 或浏览器自动化实际打开 HTML 目测**一遍：控件能不能点、提交按钮有没有发消息、深色下能不能看。**为什么**：check 只验静态结构，验不了运行时行为；盲写 + 自检 + 可选浏览器目测是 Q16 定下的调试闭环。注意直接打开磁盘文件看不到盖章值，要经伺服 URL 或注入占位符值来目测。

## 9. 版本管理引导

- 用户侧的版本信息在侧边栏「Web 应用」面板（应用列表、当前部署版本/分支、仓库状态）。
- 用户问到版本细节时，引导他**与你对话**了解（对模型 = 工具返回值，对用户 = 面板 + 对话），不要替他操作面板。**为什么**：Q13 定下的分工——面板负责展示，细节解释走对话。
- 删除应用（面板入口）= 移除目录 + 注册表条目；这不是你能代劳的，用户问起时说明即可。
